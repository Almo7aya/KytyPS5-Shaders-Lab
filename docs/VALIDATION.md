# Testing and validation

Default CTest checks test extraction and compiler behavior without executing a game or creating
a GPU device. Explicit Vulkan tests do create a device. All checked-in test inputs are synthetic
fixtures generated by the C++ test program.

## Reproduce the checks

After building, run the applicable suite:

```powershell
ctest --test-dir build --output-on-failure
ctest --test-dir build-kyty -R '^shader_lab_' --output-on-failure
```

The standalone build registers seven tests. The source-linked build adds real compiler and Vulkan guard tests:

| Test | Coverage |
| --- | --- |
| `shader_lab_unit` | Binary parsers, hashes, provenance, resume, subprocess isolation and report generation |
| `shader_lab_help` | CLI startup and documented options |
| `shader_lab_workflow` | Complete two-folder CLI, resume, output protection and error handling |
| `shader_lab_semantic` | Automatic independent CPU references, deterministic patterns, wraparound/unchanged-byte checks, partial refusals, fixture/hash matching, GPU opt-in and outcome aggregation; no device execution |
| `shader_lab_performance_report` | Serial/parallel evidence equivalence, shared-object races, resume, limits and game-specific report membership |
| `shader_lab_game_identification` | Required regular eboot, param localization/ID/version, nested roots, missing/bad metadata, duplicate titles, resume metadata refresh and legacy report migration |
| `shader_lab_cpu_reference` | Fixture suite plus independent integer CPU execution, fixed output vectors and unsupported-state checks |
| `shader_lab_real_kyty` | Fixture suite plus a synthetic compute shader translated by Kyty and validated with SPIRV-Tools |
| `shader_lab_workflow_real` | Two-folder CLI with the bundled real compiler, including SPIR-V validation and HTML output |
| `shader_lab_vulkan_guard` | Explicit opt-in guards; no GPU device execution |

The integration invocation repeats fixture checks; reported check counts are not additive.
The broad fixture suites include long-path checks and require Windows `LongPathsEnabled` policy.
The focused CLI suites can be run independently without changing that system setting:
`ctest --test-dir build-kyty -R '^shader_lab_(help|workflow.*|semantic|performance_report|game_identification)$' --output-on-failure`.
Passing those focused tests does not establish that the full suite passes on the same host.
Zstandard fixtures are enabled only when that adapter is built. Check counts may grow as coverage
is added; use the test output from your build as the authoritative result.

## Fixture coverage

- Diagnostic saturation continues extracting later shaders and counts suppressed records;
  nested container diagnostics remain bounded. Unknown-size Zstandard frames stream across
  multiple chunks while existing expansion/depth/member limits remain tested.
- Explicit local Vulkan route: `shader-lab-tests --semantic-vulkan PATH_TO_SHADER_VULKAN_REPLAY`.
  This creates a device and tests real compute dispatch, independent CPU/golden comparisons,
  and the main command's match/mismatch reporting, including automatic generation without an
  input semantics index. It is not part of default CTest.

- Parallel file scanning against serial output, including identical shared shaders across games,
  stable origin ordering, content-verified resume and file limits. The optional
  `shader-lab-tests --performance-report PATH_TO_PREVIOUS_SHADER_LAB` invocation compares a saved
  previous CLI with the sibling updated CLI over the same 64 MiB synthetic input and checks
  hashes, extracted identities and provenance. Timing is observational, not a speed assertion:
  warm filesystem caches and synthetic layouts do not predict full-game/storage performance.
- Per-game report indexes, zero-shader games, shared shader membership, per-game file counts and
  coverage finding ownership. Visual browser checks are separate from these C++ data tests.
- One-command folder analysis: bundled-worker discovery from another working directory, paths with
  spaces, positional/named forms, extraction/compilation/clustering/report output, empty inputs,
  resume, read-only inputs, failure-stage recording, missing/broken workers, folder overlap,
  unrelated-output protection and concurrent-run rejection. The real compiler suite also drives
  the complete two-folder CLI with a synthetic compute shader and requires validated SPIR-V.
- Known hash vectors, malformed headers, truncated/overflowing ELF sections and ambiguous pairs.
- Clear SELF segment reconstruction and rejection of unsupported encrypted segments.
- Clear SELF block fixtures with stored/zlib mixtures, partial last blocks, linked extent
  tables, optional digests, corrupt padding/overlaps, encrypted metadata and archive nesting.
- Bounded Zstandard payload extraction when enabled.
- ZIP stored/Deflate members, optional data-descriptor signatures, CRC failures,
  encryption notices, hostile member names, nested archives and explicit ZIP64 gaps.
- Multi-context campaigns, per-context resume, invalid plans and context-dependent failures.
- Exact recorded output comparisons, float32 policies, image layouts, identity mismatches
  and evidence containment. These are comparator tests, not GPU conformance tests.
- Isolated execution protocol with verified initial buffers/images, guest wave/EXEC and dispatch
  forwarding, fresh attempts, durable receipts, reference identity, malformed/stale responses,
  output-set/hash/size checks, path containment, input-mutation detection and process deadlines.
  The GPU opt-in test uses a protocol test double and never creates a device. It proves the
  application gate, not GPU isolation, shader execution or oracle independence.
- Actual independent CPU interpretation of a synthetic integer/global-buffer program, wave32/64,
  masked/empty EXEC, fixed arithmetic/bitwise boundary vectors, undefined/pending register checks,
  memory bounds, conflicting accesses and truncated programs. Linux CI independently assembles
  the kernel with LLVM's GFX10.3 assembler. These do not certify RDNA hardware behavior.
- Declared host-profile validation and emitted-requirement checks: unknown/disabled features,
  subgroup stage/operation support, float widths, workgroup limits and extension requirements.
  Real-worker fixtures exercise host32/host64 lowering and distinguish structural validation
  success from host-property rejection. No Vulkan device is queried or created by these tests.
- Duplicate origins, incremental scan reuse and shader-hash lookup.
- Worker protocol, resumable results, failure isolation and timeout termination.
- Portable repro relocation/replay, selected-profile identity, fresh attempts, overwrite
  protection, tampered objects/profiles, artifact path containment and explicit older-run deadlines.
- Failure reduction with a synthetic worker: necessary input retention, same-status/different-reason
  rejection, instruction PC preservation, fresh confirmations, bounded search and invalid inventories.
- Source-linked reduction of a reserved SOPP diagnostic, including replacement of an unrelated
  two-dword literal instruction without moving the failing PC. This is compiler triage, not GPU testing.
- Versioned compiler-library identity, smaller selected source set, and unchanged real-worker
  translation/validation and reduction checks through the thin process entry point.
- Synthetic pass-prefix bisection at the first/middle/last boundaries and after emission,
  changed-assertion rejection, invalid/missing traces, fresh workers and output protection.
- Real compiler tracing with unchanged SPIR-V, every requested catalog stop with IR hashes,
  invalid checkpoint rejection, and an upstream invalid-scalar-pair assertion localized to
  frontend translation. These exercise actual compiler calls, not a mock pass implementation.
- Deep filesystem paths exceeding the legacy Windows path limit; the hosted Windows runner
  enables the required OS policy and all three executables embed a long-path-aware manifest.
- Deep-path subprocess creation with absolute request/output paths and recorded actual working
  directory; Windows must use a short ancestor even when long-path file operations are enabled.
- Captured compute register ordering, all incomplete PM4 prefixes, missing state, address identity,
  predication/custom/indexed command rejection, numeric bounds and dispatch-mode validation.
- Real compute preparation through the selected upstream register decoder and `PrepareProgram`,
  including user-data overwrites, wave/workgroup/LDS metadata, dispatch-thread dimensions and
  rejection of conflicting probe overrides.
- Pixel input normalization, explicit/defaulted field tracking, numeric/array bounds, VGPR
  overlap rejection and dual-source mapping consistency. Real compiler fixtures exercise custom
  barycentrics, no-perspective interpolation, alpha-remap versus guest dual-source output, and
  sample-mask export inhibiting early fragment tests; these inspect emitted modules, not rendering.
- Report data joins, empty/extraction-only datasets and unknown/unmatched outcomes.
- HTML/script escaping, malformed UTF-8, exact 64-bit origin offsets and safe artifact URLs.

Windows x64 builds are tested with clang-cl and Ninja. GitHub Actions also builds and runs
the lightweight fixture suite on Linux. New development-branch checks require a successful
run at that commit before being treated as validated; inspect the job results, not just this list.

## Report review checklist

Open a generated report and verify:

1. Corpus-wide counts remain unchanged while case filters are applied.
2. Search, outcome/stage/source filters, sorting and continuous scrolling reach every matching case.
3. Every outcome explains its evidence and limits; unknown results never become passes.
4. The compiler journey distinguishes phase progress from semantic correctness.
5. Source provenance, diagnostics and captured profile details remain available offline.
6. Diagnostic text is safely escaped and links point only to permitted artifacts.
7. Empty datasets and mobile widths remain usable without horizontal overflow.
8. No external assets, network requests or browser errors occur.

Also check keyboard selection (Up/Down, Home/End), evidence-tab navigation (Left/Right, Home/End),
selection preservation across filters/sorts and tab preservation across shader changes. Large-list
tests should reach the final case while keeping the rendered row count bounded. Verify that logs,
profiles, source evidence and raw results are reachable without nested collapsible panels.

The continuous-list browser test has exercised 20,000 synthetic cases, including selecting the
last case, filtering to a single match, and maintaining fewer than 30 rendered case rows at the
tested desktop viewport. Desktop/mobile checks also cover all evidence tabs, artifact links,
searchable source findings, unknown outcomes, empty states and script-injection escaping.

Automated browser checks and desktop/mobile visual review have been performed for the report UI.
Use synthetic fixtures when contributing reproductions, screenshots or regression tests.

## What these checks do not prove

A structurally valid SPIR-V module does not prove equivalent output, memory behavior, numerical
semantics, synchronization or game compatibility. Probe profiles may omit real runtime state;
failures under those assumptions are investigation leads rather than confirmed emulator bugs.

Recorded reference-output comparison and an external-backend execution harness are implemented,
with a separate bounded CPU integer backend, fixed golden vectors, and experimental Vulkan
buffer-compute execution integrated into the main command. Broader ISA/graphics execution
and trusted hardware reference corpora are not yet supplied. The execution test double is only
protocol evidence. Repro replay invokes the compiler, not a GPU
or the original game. Bounded captured compute
state replay is supported, but full PM4/state replay, all graphics
stages, arbitrary archive decoding and semantic equivalence remain outside the current coverage.
Generated SPIR-V is not a directly importable emulator pipeline cache.
